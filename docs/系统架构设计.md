# 系统架构设计

## 1. 项目概述

基于 Go 语言的商品库存与秒杀系统，覆盖六次作业（HW1–HW6）的渐进式架构演进：

| 阶段 | 对应作业 | 核心能力 |
|------|----------|----------|
| 1. 单体模块化 | HW1 | Handler/Service/Repository 三层；JWT 认证；GORM 数据访问 |
| 2. 容器化 + 负载均衡 + 动静分离 | HW2 | Docker、docker-compose、Nginx 三种 LB 算法、JMeter 压测 |
| 3. 分布式缓存 + 读写分离 | HW2/HW3 | Redis Cache-Aside（穿透/击穿/雪崩防护）、PostgreSQL 主从 + GORM DBResolver |
| 4. 消息队列 + 秒杀 | HW4 | Kafka 异步下单、Redis 库存预扣、雪花算法、幂等控制、乐观锁防超卖 |
| 5. 微服务拆分 + Saga | HW5 | order/inventory/payment 三服务独立库、事务性 Outbox、事件驱动 Saga、补偿 |
| 6. 服务注册 + 流量治理 | HW6 | Nacos 注册/发现/动态配置、Go API 网关、sentinel-golang 限流/熔断/降级 |

## 2. 服务拆分

### 2.1 单体阶段（HW1–HW4）的逻辑模块

| 模块                     | 职责               | 核心能力                              |
| ------------------------ | ------------------ | ------------------------------------- |
| **用户 (User)**          | 用户认证与信息管理 | 注册、登录、JWT 签发、用户资料 CRUD   |
| **商品 (Product)**       | 商品目录管理       | 商品 CRUD、分页查询、Redis 缓存装饰器 |
| **库存 (Inventory)**     | 库存管控           | 库存设置、乐观锁扣减、库存归还        |
| **订单 (Order)**         | 订单 + 秒杀        | 同步下单（Saga）、Kafka 异步秒杀、幂等 |

### 2.2 微服务阶段（HW5+）的物理拆分

| 服务                  | 端口  | 数据库         | 职责说明 |
| --------------------- | ----- | -------------- | -------- |
| **order-service**     | 8081  | order_db (主+从) | 用户、商品（只读视图）、订单、秒杀；Outbox relay |
| **inventory-service** | 8082  | inventory_db   | 库存的真实写入与状态机（available → locked → sold） |
| **payment-service**   | 8083  | payment_db     | 模拟支付；动态配置 `success_rate` 控制成功率 |
| **gateway** (HW6)     | 8000  | —              | API 入口；Nacos 服务发现；sentinel 限流/熔断/降级 |

### 3.3 阶段 3：分布式缓存 + 读写分离（HW2/HW3）

```text
                          Client
                            │
                       ┌────▼────┐
                       │  Nginx  │ :80（动静分离）
                       └────┬────┘
                       ┌────▼────┐
                  ┌────│  App-1  │
                  │    └─────────┘
              ┌───┘
              │
   ┌──────────▼──────────┐  ┌──────────────┐  ┌──────────────────┐
   │   Redis :6379       │  │ PG Master    │  │ PG Replica        │
   │ ── Cache-Aside ──   │  │   :5432 写  │  │   :5433 读       │
   │ ── 穿透/击穿/雪崩 ── │  │              │  │ (DBResolver Random) │
   └─────────────────────┘  └──────────────┘  └──────────────────┘
```

要点：
- `CachedProductService` Decorator 封装：缓存空值（穿透）+ singleflight 合并并发（击穿）+ 5min ± 0~60s 抖动 TTL（雪崩）
- GORM `DBResolver` 插件：写操作路由 Master，读操作随机路由 Replica；Replica 缺失时自动退化为单库

### 3.4 阶段 4：Kafka 异步秒杀（HW4）

```text
Client ─POST /seckill──▶ App
                         │
                         ├─ ① Redis SETNX 幂等校验 (user+product, 24h TTL)
                         ├─ ② Redis DECRBY 原子预扣库存（毫秒级）
                         ├─ ③ Snowflake 生成 order_no
                         ├─ ④ Kafka 投递 SeckillRequest
                         └─ ⑤ 立刻返回 "排队中" + order_no

Kafka Consumer 异步：
   DB 事务 → 乐观锁扣库存 + 创建订单
   成功 → Redis 标记 SUCCESS
   失败 → 回滚 Redis 库存 + 删除幂等键
```

Saga 主流程：
```

                                      │

                ▼                                                  │
          ORDER_CANCELLED ──▶ 库存回退                                ▼
                                                          inventory: locked → sold
```

### 3.6 阶段 6：服务注册发现 + 流量治理（HW6）

```text
                    Client
                      │
                ┌─────▼──────┐
                │   Nginx    │ :80   静态资源
                │            │       /api/* → gateway
                └─────┬──────┘
                      │
                ┌─────▼──────┐
                │  Gateway   │ :8000   sentinel 限流/熔断/降级
                │   (Go)     │←──┐
                └──┬───┬───┬─┘   │ Subscribe / SelectInstances
                   │   │   │     │
            ┌──────▼┐ ┌▼───▼─────▼─┐
            │ order │ │  Nacos     │
            │  /inv │ │  :8848     │
            │  /pay │ └────────────┘
            └───────┘   注册中心 + 配置中心
```

要点：
- 服务启动 → `RegisterInstance(ip,port,serviceName)`，进程退出 → `DeregisterInstance`
- Gateway 通过 `Subscribe` 监听实例变化（push）+ 5s 轮询（pull 兜底）
- sentinel-golang 在 Gateway 入口埋点：
  - **限流**：`/api/v1/seckill` 50 QPS Reject
  - **熔断**：错误比例 50% / 10s 窗口 / 最少 10 次请求 / 5s 半开探测
  - **降级**：被拦截或熔断打开时统一返回 `503 + JSON envelope`，作为 fallback

## 4. 模块内部分层架构

每个业务模块内部均遵循统一的三层结构：

```
┌─────────────────────────────────┐
│  Handler 层（HTTP 路由处理）      │  ← 接收请求、参数校验、调用 Service
├─────────────────────────────────┤
│  Service 层（业务逻辑）           │  ← 核心逻辑、事务编排、跨模块调用
├─────────────────────────────────┤
│  Repository 层（数据访问）        │  ← GORM 数据库操作、SQL 查询
└─────────────────────────────────┘
                │
                ▼
          PostgreSQL
```

**设计原则：**

- 模块间**只通过 Service 层接口调用**，不直接访问其他模块的 Repository
- 统一响应格式：`{ code, message, data }`
- 统一错误处理：使用类型化哨兵错误（如 `ErrUserExists`、`ErrStockInsufficient`）
- **跨服务**调用一律走事件（Outbox + Kafka），不引入 RPC，避免分布式事务两阶段提交
