# 技术栈选型说明

## 1. 核心技术栈

### 1.1 编程语言：Go 1.23+

| 维度           | 说明                                                                                           |
| -------------- | ---------------------------------------------------------------------------------------------- |
| **选型理由**   | 高性能、原生并发（goroutine）、编译为单二进制文件                                              |
| **适用场景**   | 秒杀系统需要高并发处理能力，Go 的 goroutine 模型天然适合                                       |
| **容器化优势** | 编译产物为单个静态二进制，Docker 镜像可基于 alpine 极小化（< 20MB）                            |
| **备选方案**   | Java (Spring Boot) — 生态更成熟但运行时资源占用较大；Node.js — 单线程模型在 CPU 密集场景下受限 |

### 1.2 Web 框架：Gin

| 维度             | 说明                                                                  |
| ---------------- | --------------------------------------------------------------------- |
| **选型理由**     | Go 社区最流行的 HTTP 框架，性能优异，中间件生态完善                   |
| **核心能力**     | 路由分组、中间件链、参数绑定与校验、JSON 序列化                       |
| **项目中的使用** | 路由注册、JWT 认证中间件、请求日志中间件、错误恢复中间件              |
| **备选方案**     | Echo — 功能类似但社区规模略小；标准库 net/http — 功能原始，需大量手写 |

### 1.3 ORM：GORM

| 维度             | 说明                                                                    |
| ---------------- | ----------------------------------------------------------------------- |
| **选型理由**     | Go 最成熟的 ORM，功能丰富，文档完善，对初学者友好                       |
| **核心能力**     | 自动迁移（AutoMigrate）、关联查询、钩子函数、事务支持                   |
| **项目中的使用** | 数据库表自动创建与迁移、CRUD 操作封装、事务管理（订单创建）、乐观锁实现 |
| **备选方案**     | sqlx — 更轻量但需手写 SQL；Ent — Facebook 出品但学习曲线陡              |

### 1.4 数据库：PostgreSQL 16

| 维度             | 说明                                                                            |
| ---------------- | ------------------------------------------------------------------------------- |
| **选型理由**     | 完整 ACID 支持、丰富数据类型（JSON、数组）、GORM 完整支持                       |
| **核心能力**     | 事务隔离级别、行级锁、MVCC 并发控制、丰富的索引类型                             |
| **项目中的使用** | 用户/商品/库存/订单四张核心表，事务保证订单创建的原子性                         |
| **备选方案**     | MySQL — 同样适用但 PostgreSQL 在高级特性上更丰富；SQLite — 不适合多实例并发写入 |

## 2. 认证与安全

### 2.1 认证方案：JWT (golang-jwt/jwt)

| 维度           | 说明                                                                                |
| -------------- | ----------------------------------------------------------------------------------- |
| **选型理由**   | 无状态认证，天然适合多实例部署（不依赖 session 共享）                               |
| **实现方式**   | 登录成功后签发 JWT Token，Token 中包含 user_id、username、role                      |
| **多实例优势** | Nginx 负载均衡到任意后端实例都可验证 Token，无需共享 Session 存储                   |
| **备选方案**   | Session + Redis — 需额外部署 Redis 做 Session 共享；OAuth2 — 本项目不需要第三方登录 |

### 2.2 密码加密：bcrypt (golang.org/x/crypto)

| 维度         | 说明                                            |
| ------------ | ----------------------------------------------- |
| **选型理由** | Go 官方扩展库，安全可靠，自带盐值，抗彩虹表攻击 |
| **实现方式** | 注册时对密码 bcrypt 哈希存储，登录时比对哈希值  |

## 3. 配置管理：Viper

| 维度           | 说明                                                                    |
| -------------- | ----------------------------------------------------------------------- |
| **选型理由**   | 支持 YAML / 环境变量 / 命令行参数多种配置源，优先级可控                 |
| **配置优先级** | YAML 文件（默认值） < 环境变量覆盖（前缀 `FLASH_SALE_`）                |
| **容器化适配** | Docker 环境通过环境变量注入配置（如数据库地址、端口），无需修改配置文件 |

配置示例：

```yaml
# config/config.yaml
server:
  port: 8080

database:
  host: localhost
  port: 5432
  user: flashsale
  password: flashsale123
  dbname: flashsale
  sslmode: disable

jwt:
  secret: "your-secret-key"
  expire_hours: 24
```

环境变量覆盖示例：

```bash
FLASH_SALE_SERVER_PORT=8081      # 覆盖 server.port
FLASH_SALE_DATABASE_HOST=postgres # 覆盖 database.host
```

## 4. 容器化与部署

### 4.1 Docker

| 维度         | 说明                                                              |
| ------------ | ----------------------------------------------------------------- |
| **选型理由** | 标准容器化方案，环境一致性，便于多实例部署                        |
| **构建策略** | 多阶段构建 — 第一阶段 Go 编译，第二阶段 Alpine 运行，最终镜像极小 |
| **镜像基础** | 构建阶段：`golang:1.26-alpine`；运行阶段：`alpine:latest`         |

### 4.2 Docker Compose

| 维度         | 说明                                                    |
| ------------ | ------------------------------------------------------- |
| **选型理由** | 单机多容器编排，一键启动完整开发/测试环境               |
| **编排内容** | PostgreSQL + App 实例 ×2 + Nginx                        |
| **服务发现** | 容器间通过服务名通信（如 `postgres`、`app-1`、`app-2`） |

### 4.3 Nginx

| 维度         | 说明                                                               |
| ------------ | ------------------------------------------------------------------ |
| **选型理由** | 高性能反向代理，支持多种负载均衡算法，动静分离能力成熟             |
| **负载均衡** | 支持轮询（默认）、加权轮询、IP Hash 三种算法                       |
| **动静分离** | 静态文件（HTML/CSS/JS）由 Nginx 直接返回，API 请求转发后端         |
| **备选方案** | Traefik — 自动服务发现但配置复杂度高；HAProxy — 功能强但学习成本高 |

## 5. 分布式缓存：Redis 7（HW2/HW3/HW4）

### 5.1 客户端：go-redis/v9

| 维度 | 说明 |
|------|------|
| **选型理由** | 官方维护，原生支持 Redis 6+ Streams/RESP3，Pipeline 与 Lua 脚本简洁 |
| **项目使用** | 商品详情缓存、秒杀库存预扣（DECRBY）、幂等键（SETNX）、秒杀结果状态 |
| **故障降级** | Redis 调用失败时 `CachedProductService` 回落到 DB 直接查询，返回带 `[CACHE_MISS]` 日志标识 |

### 5.2 缓存三大问题的应对

| 问题 | 实现 |
|------|------|
| **穿透** | 命中数据库空结果时缓存 null marker (TTL 60s)，挡住对不存在 ID 的恶意打点 |
| **击穿** | `golang.org/x/sync/singleflight` 把同 key 并发请求合并成一次 DB 查询 |
| **雪崩** | 基础 TTL 5min + 0~60s 随机抖动，错峰过期 |

### 5.3 测试工具：miniredis/v2

| 维度 | 说明 |
|------|------|
| **选型理由** | 内存 Redis 替身，单元测试无需真实 Redis 进程 |
| **项目使用** | `pkg/cache` 与 `internal/product/cached_service` 单测 |

## 6. 读写分离：GORM DBResolver（HW3）

| 维度 | 说明 |
|------|------|
| **选型理由** | GORM 官方插件，对业务代码完全透明（不需要分库写法） |
| **路由策略** | 写自动走主库，读使用 `dbresolver.RandomPolicy` 随机选从库 |
| **优雅降级** | 配置 `database.replicas` 为空时插件不挂载，自动退化为单库模式 |
| **备选方案** | go-zero 的多 DSN dao；shardingsphere-proxy（侵入数据库网络层） |

## 7. 消息队列：Apache Kafka（HW4/HW5）

### 7.1 客户端：IBM/sarama

| 维度 | 说明 |
|------|------|
| **选型理由** | 纯 Go、无 CGO；原生支持消费者组；社区主流 |
| **Producer** | 同步模式 + `WaitForAll` ACK，确保事件不丢；写入失败由 Outbox relay 重试 |
| **Consumer** | 消费者组模式，按主题水平扩容；处理失败不提交 offset，重试到成功为止 |
| **备选方案** | Confluent Go Client（依赖 librdkafka，CGO）；segmentio/kafka-go |

### 7.2 主题划分

| Topic              | Producer            | Consumer                            |
|--------------------|---------------------|-------------------------------------|
| `order-events`     | order-service       | inventory-service / payment-service |
| `inventory-events` | inventory-service   | order-service                        |
| `payment-events`   | payment-service     | order-service                        |

## 8. 雪花算法订单 ID（HW4）

| 维度 | 说明 |
|------|------|
| **选型理由** | 趋势递增 ID 对 BTree 索引友好；天然分布式；无需中心化 ID 服务 |
| **位分布** | 41bit 时间戳 + 10bit 节点 ID + 12bit 序列号（每毫秒每节点 4096 个 ID） |
| **节点 ID** | 通过 `FLASH_SALE_SNOWFLAKE_NODE_ID` 环境变量注入，避免容器副本冲突 |

## 9. 分布式事务：事务性 Outbox + 事件驱动 Saga（HW5）

| 维度 | 说明 |
|------|------|
| **选型理由** | 比 2PC 简单可靠；不需要分布式协调器；天然适配 Kafka |
| **写一致性** | 业务表写入与 outbox 事件落盘在**同一本地事务**中，保证原子 |
| **投递保证** | 后台 relay 协程轮询未发送的 outbox 行投递 Kafka，至少一次（At-Least-Once） |
| **重复消费** | 事件携带唯一 `EventID`；消费者侧基于业务键幂等（订单状态机 + 库存乐观锁） |
| **补偿** | 失败事件触发反向 Saga：`PAYMENT_FAILED` → `ORDER_CANCELLED` → 库存回退 |

## 10. 服务注册发现 + 配置中心：Nacos 2.3 + nacos-sdk-go/v2（HW6）

| 维度 | 说明 |
|------|------|
| **选型理由** | 原 Spring Cloud 作业要求 Nacos；Go SDK 同样官方维护；标准 RESTful + gRPC 接口 |
| **使用方式** | 三个服务启动 `RegisterInstance`，关闭 `DeregisterInstance`；网关用 `Subscribe` 订阅实例变更 |
| **动态配置** | `payment-service` 监听 Data ID `payment.success_rate`，运维改 Nacos 配置即热生效（无需重启） |
| **架构无关性** | Nacos 服务端是 Java，但只暴露协议；Go 客户端能力与 Spring Cloud Alibaba 等价 |
| **备选方案** | etcd（无配置中心）、Consul（无配置 watch 一体化）、Spring Cloud Gateway + Nacos（Java 栈） |

## 11. API 网关：Go (Gin + httputil.ReverseProxy)（HW6）

| 维度 | 说明 |
|------|------|
| **选型理由** | 不引入 Spring Cloud Gateway / Kong / Apisix，保持纯 Go 技术栈一致 |
| **核心组件** | Nacos `Subscribe` 推 + 5s 轮询拉的双保险实例池；`httputil.NewSingleHostReverseProxy` 透明转发 |
| **路由匹配** | 长前缀优先（`/api/v1/seckill` 优先于 `/api/v1`）；单个路由对应单个 sentinel resource |
| **观测** | `/gateway/instances` 端点返回当前实例池快照，便于排查发现链路 |

## 12. 流量治理：alibaba/sentinel-golang（HW6）

| 维度 | 说明 |
|------|------|
| **选型理由** | Sentinel 官方 Go 版本，规则语义与 Java 版一致；配置简单且文档完善 |
| **限流** | `flow.Rule { Threshold: 50, ControlBehavior: Reject }` 应用到 `route:seckill` |
| **熔断** | `circuitbreaker.Rule { Strategy: ErrorRatio, Threshold: 0.5, MinRequestAmount: 10, StatIntervalMs: 10000, RetryTimeoutMs: 5000 }` |
| **错误打点** | 网关 `proxy.ModifyResponse` 把上游 5xx 也算作 sentinel 错误，使熔断对真实下游故障敏感 |
| **降级** | 拦截或熔断打开时统一返回 `{code:503, message:"service degraded..."}` 的 fallback JSON |
| **备选方案** | Hystrix-go（停止维护）；resilience4go；自研 token bucket（无熔断/降级一体化） |
